# v1.3 A2A 双通道:轻量消息 + 正式任务 — 设计规格

> 本文档定义 v1.3 的完整实现规格:A2A 从单一"任务"通道拆分为**双通道**——轻量消息(纯沟通,无记录)与正式任务(完整状态机,强制全流程)。基于 v1.2 规格扩展。
> 实施方式与前序版本相同:先对齐本规格,后端由宿主开发者实施,前端如需配合由外包实施(契约在本文件)。

---

## 1. 背景与动机

### 1.1 卡死任务复盘(7b796f55)

线上观察到一个任务永久卡在 `working`:

```
任务 7b796f55  initiator=三号  executor=PM
内容:"你好 PM,我是三号。请给我派发一个新任务,我会按任务要求完成……"
```

- 三号用 `dispatch_task` 发送的是一句**沟通请求**(让 PM 派任务),不是工作指令。
- 由于 Agent Bus 里"任务即消息",这条请求被记为正式任务行,投递到 PM 的 inbox 并被认领(`submitted → working`)。
- PM 把它当作普通消息处理了(随后向三号派发了新任务 3),但从未对 7b796f55 调用 `report_task` —— 因为对 PM 而言它只是一句话,不是需要交差的工作。
- 状态机里 `working` 只有 4 个出口:`completed` / `input-required` / `failed` / `canceled`。没有任何一方有动机触发其中任何一个 → **永久卡死**,只能靠 2 小时超时兜底为 `failed(timeout)`。

**根因**:`dispatch_task` 承载"纯消息"语义时,会生成一条必须走完 report → settle 生命周期的 ledger 行,却没有"纯消息"通道;且 `working` 卡死只有超时一个兜底,对"消息型任务"尤其容易触发。

### 1.2 结论:双通道

A2A 应有两个途径:

| | 通道一:轻量消息 | 通道二:正式任务 |
|---|---|---|
| 工具 | `send_note` | `dispatch_task` |
| 用途 | 沟通、提问、确认、协调 ping | 派发必须交付可验收成果的工作 |
| 任务记录 | **无** | 有(ledger 行,完整状态机) |
| 状态机 | 无(发送即完成) | submitted → working → completed → settle,含 rework/cancel/request_input/DAG |
| 验收 | **不强制** | **强制**(reviewer settle) |
| 恢复 | **不强制**(无超时、无取消) | 超时 → failed;取消 → canceled |
| 面板 | 不出现(会话日志即记录) | 任务卡片 + 状态徽章 |
| 占队列槽位 | 不占 | 占(`maxPendingPerAgent`) |

**选用准则**(写入模型面 USAGE_TEXT):需要对方产出结果并接受验收 → `dispatch_task`;只是沟通 → `send_note`。二者投递机制相同(followup 收件箱),区别只在是否落账、是否强验收。

**工具命名**:两个通道的工具名都是本插件独有、不与其他插件共享:`dispatch_task`(正式任务)与 `send_note`(轻量消息)。注意 `send_note` **不是** `send_message`——harness 基础包(dsh-tool-subagent-control)在全局注册了 `send_message`(给后台 subagent 续会话),同名注册会被工具注册表拒绝(实测:运行环境中 `send_message` 绑定 subagent 语义,agent-bus 的同名工具被顶掉),因此消息通道必须用独有名。

## 2. 通道一:轻量消息(`send_note`)

### 2.1 语义

- 发送即完成:消息投递到接收方 inbox,无 ledger 行、无状态、无超时、无取消。
- 接收方把消息当作普通对话输入处理,**回复就是正常文字对话**;是否回复、何时回复完全自由。
- 消息不占 `maxPendingPerAgent` 槽位,不进 `list_tasks`,不上任务面板。

### 2.2 交付格式(header)

**所有渠道注入的提示词开头统一带调用工具名**;任务型交互必须附带任务 id:

```text
# 消息(通道一):
<dsh-agent-bus-message tool="send_note" sender="<sessionId>" id="<messageId>">
<content>

# 任务/通知(通道二,任务 id 必带):
<dsh-agent-bus task="<taskId>" tool="<source>" sender="<sessionId>">
<content>
```

`tool` 取值与接收方解读:

| tool | 渠道 | 接收方动作 |
|---|---|---|
| `dispatch_task` | 手动派发 | 执行任务 → `report_task` |
| `scheduler` | DAG 自动派发 | 同任务 |
| `report_task` | 完成通知(reviewer 侧) | `settle_task` 验收 |
| `settle_task` | 验收结果 / 重做指令 | success:结束;failure:重做 → 再 report |
| `cancel_task` | 取消通知(worker 侧) | 交已完成部分摘要 |
| `reminder` | turn-end 提醒 | 无需单独动作,欠 report 就交 |
| `timeout` | 超时通知(initiator 侧) | 决定是否重派 |

- 消息 source 使用独立 kind `agent-bus-message`(表单仍为 `relay`),UI/日志可区分,`agent/inbox/claimed` 监听器按 message.id 查 ledger 找不到行 → 天然忽略,无副作用。
- 历史格式 `<dsh-agent-bus sender="..." task="...">`(无 tool)由本次升级废弃,运行中的旧投递不再产生。

### 2.3 回复路径

B 收到消息后如需回复,用 `send_note` 回复给 header 中的 `sender`(可选,不强制)。消息通道的回环完全由对话双方自行驱动;A 侧若想知道 B 已读/已回,只能靠 B 主动回消息——这是"不强制验收和恢复"的直接代价,与第 1.2 节表格一致。

### 2.4 权限与限流

| 项 | 规则 |
|---|---|
| 目标校验 | 复用 `authorizePeer`:必须 live、必须同 workspace、禁止发给自己 |
| 内容卫生 | 复用 `admitContent`:`maxContentLength` 上限,过 sanitize(去控制字符) |
| 限流 | 独立滑窗限流器 `maxMessagesPerMinute`(默认 20/分钟/发送方),与任务限流器互不共享配额 |
| 投递失败 | 目标不在线 → 工具报错拒绝(与任务一致);已投递消息不可撤回 |

### 2.5 工具契约

```
send_note(target: string, content: string)
→ { delivered: true, messageId: string }
```

- `target`:`list_peers` 返回的 session id。
- `content`:消息正文,同内容卫生规则。
- 返回 `messageId` 供发送方留痕(会话日志中也可见)。

### 2.6 不做什么

- 不做消息记录表(会话日志即记录)——面板、`list_tasks`、统计均不感知消息。
- 不做已读回执、不做超时提醒、不做消息删除。
- 不做 `mode=steer` 打断式消息(打断只属于任务 `dispatch_task`)。

## 3. 通道二:正式任务(`dispatch_task`)

现状不变,重申边界(详见 v1.2 规格):

- 完整状态机:submitted → working → completed(待验收)→ settle success/failure;failed/canceled 终态;rework 同 id。
- 强制验收:completed 必须由 reviewer `settle_task` 结算;只有 initiator(或指派 reviewer)能 settle/cancel。
- DAG:`depends_on`、自动排期、失败传播、`edit_task` 全部保留。
- **行为修正(本次)**:`dispatch_task` 工具描述与 USAGE_TEXT 明确"沟通请求不属于任务",引导模型在纯沟通场景走 `send_note`。

---

## 4. 模型面指引(USAGE_TEXT 变更)

新增/修改要点:

1. 新增 `send_note` 段落:轻量消息,无任务记录、无验收、无恢复;收到 `<dsh-agent-bus-message>` header 的消息时直接文字回复(如需回复用 `send_note` 回给 sender)。
2. `dispatch_task` 段落补充边界:派发的是**必须交付可验收成果**的工作;沟通、提问、确认请用 `send_note`——否则会产生一条永远等不到 report 的任务,阻塞执行方队列。
3. 工具清单追加 `send_note`。

---

## 5. 面板

- **无变更**:消息不进面板、不进统计。会话日志是消息的唯一记录。
- 任务侧保留 v1.2 的 DAG 视图、归档分区、待验收徽章等。

---

## 6. 数据安全:ledger 备份快照(防数据丢失复发)

**背景**:线上丢失过任务 e420b249 等 v5 时代行——根因是 v1.2 升级指引"删除 agent_bus.json 重新生成",v6 重建时旧行全清,无备份可回。本次修复保险,不改变 dsh 存储行为:

- `TaskLedger.open()` 成功后,把全表行 + `taskIds` 以 JSON 快照写入 `dshHomePath('agent-bus', 'backups', 'ledger-<ISO时间戳>.json')`。
- 每次 open 写一份(数据量几 KB);只增不删,保留最近 20 份(超出删除最旧)。
- 快照是只读保险,不参与运行时读写;恢复时人工读取即可。

**规格更新**:未来 schema 版本升级(domain version bump)前,先保留现有 `agent_bus.json` 副本,再执行重建流程。

## 7. 遗留处理:卡死的 `working` 任务

7b796f55 已在运行现场:initiator(三号)已离线多日。处理路径(不需改代码):

1. **推荐**:PM 以执行方身份 `report_task` 提交摘要("已响应并派发任务 3")→ 状态推进 `completed`(面板显示「待验收」,顺便验证待验收态)→ 三号上线后 `settle_task` 结算。
2. 兜底:2 小时超时自动 `failed(timeout)`(已有)。

**防复发**(代码层已就位):

- `send_note` 通道:沟通不再产生任务行(本次实现)。
- turn-end 提醒:executor 结束一轮 turn 时若仍有 `working` 任务,每 15 分钟提醒一次调用 `report_task`(已实现)。
- 超时兜底:taskTimeoutMs(默认 2h)自动 failed + 通知 initiator(已有)。
