# v1.2 流程 DAG 可视化与自动排期 — 设计规格

> 本文档定义 v1.2 的完整实现规格:PM 拆分任务并用依赖关系建 DAG,代码自动执行排期(依赖结算后自动派发下游),面板提供 DAG 视图。基于 v1.1 规格第 8 章扩展。
> 实施方式与 v1.1 相同:先对齐本规格,后端由宿主开发者实施,前端 DAG 视图由外包实施(契约在本文件)。

---

## 1. 目标与范围

**目标**:任务从"单条派发"升级为"流程编排"。

- **节点 = 任务**:DAG 中每个节点是一条任务,经历完整流程(派发→执行→验收→结算)后标记为已结算,并释放后方依赖项。
- **自动排期**:就绪(所有前置依赖已结算)任务的派发由**代码自动执行**,不依赖人工;PM 只负责任务拆分与 DAG 制作。
- **DAG 可视化**:面板新增 DAG 视图,节点状态与台账联动。

**范围边界(本期不做)**:

| 不做 | 原因 |
|---|---|
| 多图/图生命周期管理(图删除、归档图) | 连通分量即图;图级操作属 v1.3 |
| 执行者自动选择(调度器 round-robin) | v1.2 任务创建时绑定执行者,调度器只投递 |
| 条件分支/循环/并行度限制 | 无此需求;并行天然支持(多依赖同清同时释放) |
| 重做时的依赖语义变更 | 重做(settle failure)不改变依赖集合(见 4.4) |

## 2. 数据模型(schema v6)

### 2.1 `tasks` 表增加 `dependencies`

```ts
// spec.ts — taskRecord 增加(optional,旧行兼容):
dependencies: z.array(taskId).max(16).optional(),
auto: z.boolean().optional(),   // 调度器自动派发标记
```

- `dependencies`:本任务的前置任务 id 列表,创建时一次性写入,**不可变**(无改依赖工具;改依赖=取消重建)。
- `auto`:任务由调度器自动派发时为 `true`(手动派发恒 false/缺省)。
- **domain version 4 → 5 已占用;本次 v5 → v6**。升级时删除 `agent_bus.json` 重新生成(既有流程)。
- `StoredTaskRecord` / `TaskRecord` / `NewTask` 同步。

### 2.2 校验(写入时,ledger 层)

`record()` 接受 `dependencies` 时校验,任一失败拒绝创建:

| 校验 | 规则 |
|---|---|
| 自引用 | `dependencies` 不含本任务 id |
| 环 | 加入后依赖图无环(DFS 检测;图 = 全表 dependencies 投影) |
| 存在性 | 每个依赖 id 都存在于台账 |
| 归属 | 依赖与任务同 workspace(依赖的 `workspacePath` === 本任务) |
| 上限 | ≤ 16 个前置 |

### 2.3 派生概念(不落库)

| 概念 | 定义 |
|---|---|
| `ready`(就绪) | 所有依赖已结算(`outcome === 'success'`) |
| `blocked`(阻塞) | 存在未结算依赖 |
| 图(连通分量) | `tasks[].dependencies` 的有向边集;弱连通分量即一张图 |
| 根节点 | 无依赖的任务 |

## 3. 生命周期与排期语义

### 3.1 状态机(不扩 A2A 词汇表)

```
创建(submitted, blocked 或 ready)── 调度器/手动 ──> submitted(已派发,待认领)
  │                                              │
  └── 依赖未清时拒绝派发(ledger 校验)             └──> working → completed → settle
                                                        │ success ──> 结算,释放下游
                                                        └ failure ──> submitted(重做,同 id)
```

- **不新增 `ready`/`blocked` 状态**:A2A 词汇表保持 8 态。`ready`/`blocked` 由 `dependencies` + 依赖结算状态**推导**,面板展示为徽标叠加(状态点旁小标记),模型与台账不感知。
- **派发门禁**:`dispatch_task` 对带依赖任务:依赖未全结算 → 拒绝(错误信息列出未结算依赖)。门禁在 ledger 层(工具与调度器共用同一校验函数 `blockedBy(task)`)。

### 3.2 自动排期(调度器)

**触发时机**(两路,保证收敛):

1. **事件驱动**:`settle()` success 落盘后,同步触发释放检查。
2. **启动扫查**:插件 apply 时全量扫查一次(进程重启后恢复自动排期),此后 60s 周期兜底扫查(防御:投递失败、进程漂移)。

**释放算法**(纯函数 `releaseAfterSettle(ledger, taskId)`):

```
对每个 dependent(反查依赖包含 taskId 且同 workspace 的任务):
  若 dependent 未派发(submitted)且 blockedBy(dependent) 为空(依赖全结算):
    自动派发:
      - 复用现有投递路径(buildTaskMessage + deliverTask)
      - assignedBy 保持创建者(PM 会话),assignedTo 为创建时绑定的执行者
      - ledger 行标记 auto: true(recordDelivery 时?不——投递即记录,见 3.3)
      - 通知 PM:「任务 X 的前置依赖已全部结算,已自动派发给 Y」
```

**执行者绑定**:v1.2 任务创建时 `dispatch_task.target` 必填(与现在一致),调度器不选执行者。PM 需要"先建图后派发"时,可先创建依赖未清的任务(不会投递),依赖清空后调度器投递。

### 3.3 投递与记录

带依赖任务的创建流程(与 v1.1 的 record 前投递相反):

```
手动派发(依赖已清):record(dependencies) → deliverTask → messageId 记录(现有流程不变)
创建 blocked 任务:  record(dependencies) → 不投递(messageId 缺省)
自动派发(释放):    deliverTask → recordDelivery(messageId) → auto 标记
```

- `recordDelivery` 增加可选 patch:`recordDelivery(id, messageId, { auto: true })`(仅调度器投递时传)。
- 创建时未投递的任务行:`messageId` 缺省,`submitted` 且未派发——工具 `list_tasks` 渲染不变(状态仍是 submitted),面板 DAG 视图显示"待释放"叠加。

### 3.4 重做语义

- `settle failure` → 任务回 `submitted`(现有重做),**依赖集合不变**。
- 依赖已结算的节点重做:其下游不受影响(下游已派发/执行中)——**已释放的下游不收回**。文档注明:重做是同一节点重跑,不撤销下游推进。这是显式设计决策(避免级联回滚的复杂度),如有异议在评审时提出。

## 4. 工具扩展

### 4.1 `dispatch_task` 增加 `depends_on` 参数

```
depends_on: { type: 'array', items: { type: 'string' }, maxItems: 16, description: '前置任务 id 列表;依赖未全部结算时任务仅创建不投递,调度器自动释放' }
```

行为:
- 依赖全结算(或缺省)→ 现有流程(立即投递)。
- 存在未结算依赖 → 仅 record(带 dependencies),**不投递**,返回 `status: 'submitted', queued: false, blockedBy: [未结算依赖 id]`。
- 输出 schema 增加 `blockedBy: { type: 'array', items: { type: 'string' } }`(缺省空数组)。

### 4.2 无新工具

- 建图 = 多次 dispatch(带 depends_on);改图 = 取消重建。v1.2 不引入 `create_dag`/`link_task`,减少工具面。

### 4.3 `list_tasks` / `get_task` 渲染

- `list_tasks` 行追加:`deps: [前置数]`(有依赖时)+ `blocked: 未结算依赖数`(blocked 时)。
- `get_task` 全文追加:`dependencies` 列表 + 每项结算状态 + `blockedBy` 说明。

## 5. 快照契约(v1.2 增量)

`GET /plugins/dsh-agent-bus/state` 的 `TaskView` 增加:

```ts
/** 本任务的前置任务 id(创建时写入,不可变)。 */
readonly dependencies: readonly string[]
/** 依赖本任务的任务 id(反查,面板 DAG 高亮/释放用)。 */
readonly dependents: readonly string[]
/** 未结算依赖 id 列表;空 = 就绪。 */
readonly blockedBy: readonly string[]
/** 调度器自动派发标记。 */
readonly auto: boolean
```

- `blockedBy` 由路由侧计算(依赖的 `outcome !== 'success'` 且未 canceled/failed?——定义见 5.1)。
- 面板 DAG 视图数据 = `tasks` 全量本地构建(节点=任务,边=`dependencies`),**快照不加专门 DAG 字段**。

### 5.1 依赖结算定义(blockedBy 判定)

依赖视为"已满足"当且仅当 `outcome === 'success'`。`failed`/`canceled` 的依赖**不满足**(阻塞持续)。阻塞中的依赖 failed/canceled → 依赖链死锁:**面板 DAG 视图将该节点标记为"依赖失败,阻塞"**(红色),v1.2 不做自动失败传播(PM 人工取消重建)。

## 6. 面板 DAG 视图(前端,外包实施)

### 6.1 入口

- 抽屉顶栏新增视图切换:`[列表 | DAG]`(现有列表视图为默认)。
- DAG 视图替换主界面(会话侧边栏保留?——**保留**,点选会话在 DAG 中高亮其参与节点)。

### 6.2 渲染(参照 dsh-agent-teams DependencyMap)

- 布局:分层布局(拓扑层按依赖深度排布,同层横向);参照 teams `compactDagLayout` 的紧凑算法,但**以任务内容摘要为节点标签**(不同于 teams 的短 id)。
- 节点 = 任务卡(缩小版):状态点 + 徽标 + `contentPreview` 截断 18 码点;`blocked` 节点加"等待依赖"小标记;`ready` 未派发节点描边高亮(虚线)。
- 边:有向箭头,依赖 → 被依赖(前置 → 后置)。
- 交互:悬停高亮该节点的依赖链(上游已结算=绿,未结算=黄,失败=红)+ 下游;点击固定(Esc 取消);点击节点在下方详情区展示完整任务信息(复用现有 TaskCard 展开区逻辑)。
- 节点状态点颜色复用 4.5 状态表;额外叠加:`blockedBy` 非空 → 黄边;依赖存在 failed/canceled → 红边 + "依赖失败"角标。
- 结算联动:节点结算(success)后自动变绿描边并**高亮其后置节点** 2s(释放动画,纯 CSS)。

### 6.3 panel-model 新增纯函数(可单测)

```ts
export interface DagNode { task: TaskView; depth: number }
export interface DagEdge { from: string; to: string }   // from = 前置, to = 后置
export function dagOf(tasks: readonly TaskView[]): { nodes: DagNode[]; edges: DagEdge[] }
// 只取同工作区任务;环在写入时已被 ledger 拒绝,此处仅防御性跳过环边

export function dependencyChainOf(taskId, nodes): { upstream: TaskView[]; downstream: TaskView[] }
// 上游 = 沿依赖递归;下游 = 沿 dependents 递归;失败(依赖 failed/canceled)节点标红

export function blockedByOf(task: TaskView, tasks: readonly TaskView[]): readonly string[]
// 客户端同源计算(快照已给 blockedBy,此函数供 DAG 视图局部刷新用)

export function isDeadlocked(task: TaskView, tasks: readonly TaskView[]): boolean
// 依赖中存在 failed/canceled 且该依赖未释放 → 死锁标记
```

## 7. 验收

### 7.1 单元测试(宿主端)

- 校验:自引用/环(链、环、自环)/缺失 id/跨 workspace/上限 16 → 全部拒绝。
- `blockedBy`:依赖 success 释放;failed/canceled 不释放;多依赖部分结算。
- 释放:settle success → 下游 ready 且唯一一次投递(幂等:重复 settle/重启扫查不重复派发——**派发判据:submitted 且 messageId 缺省**);已派发的下游不重复投递。
- 自动派发:messageId 写入 + auto 标记 + PM 通知发出。

### 7.2 前端单测

- `dagOf`:层深正确(链/菱形/并行)、边方向正确、空图。
- `dependencyChainOf`:上游/下游递归、死锁标记。

### 7.3 e2e(本地,扩展现有 abc 流程)

- PM 创建 3 节点链:A(无依赖)→ B(depends_on A)→ C(depends_on B),执行者分别为 二号/二号/三号。
- A 结算 → **B 自动派发**(台账 messageId 出现 + 二号收到投递)→ B 结算 → C 自动派发 → C 结算。
- 断言:全程无人工派发;每个节点只投递一次;DAG 视图节点全部结算(快照 blockedBy 全空)。
- 依赖失败路径:A failed → B 保持阻塞(blockedBy 含 A)→ 面板 DAG 标记死锁。
